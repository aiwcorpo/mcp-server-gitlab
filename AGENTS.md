# AGENTS.md

mcp-gitlab is the MCP server for self-managed GitLab in [MCP Platform](https://github.com/aiwcorpo/mcp-platform). Only the
gateway calls it (internal JWT, policy data pushed to `POST /.well-known/mcp-policy-data`); it calls GitLab REST API v4
with the caller's own token. Its interfaces follow `mcp-contracts` (`server-manifest.schema.json`,
`internal-jwt.schema.json`, `tool-error.schema.json`, `openapi/mcp-server.v1.yaml`) through `mcp-platform-starter` 4.0.0
from `mcp-starter-lib`.

## Commands

Maven needs JDK 25. If `JAVA_HOME` points to an older JDK the build fails with `UnsupportedClassVersionError`; on macOS
with Homebrew use `export JAVA_HOME=/opt/homebrew/opt/openjdk@25/libexec/openjdk.jdk/Contents/Home`.

```bash
./mvnw -B verify                    # what CI runs (GitHub, GitLab, Jenkins); all tests and the manifest file
./mvnw -B -pl mcp-app -am test -Dtest=RepositoryToolsTest -Dsurefire.failIfNoSpecifiedTests=false   # one test class
docker build -t mcp-gitlab:dev .    # image, after verify; needs a Docker daemon
```

The full verify takes about a minute. No Docker and no GitLab are needed. There is no separate lint or format step;
follow `.editorconfig`.

## Layout

- `mcp-core` (domain, ports, `GitLabPaths`), `mcp-application` (services, `JobLogText`), `mcp-integration` (REST adapters,
  resolvers, version detection), `mcp-tools` (the `@Tool` methods in `GitLabTools`, `RepositoryTools`, `IssueTools`,
  `MergeRequestTools`, `PipelineTools`, arguments, errors), `mcp-app` (Spring Boot app, config, `ManifestExport`, policies).
- `mcp-app/src/main/resources/mcp/policies/`: the Cedar schema, `resource-types.json` and policies of the `GitLab`
  namespace, including `restricted.cedar`.
- `mcp-app/src/test/java/.../app/`: tests of the whole server against `TestGateway` and `StubBackend`; module unit tests
  sit in each module's `src/test`. `mcp-app/target/mcp-manifest.json` is generated by the build; never edit or commit it.
- `mcp-app/src/test/resources/fixtures/`: `common/` plus `gitlab-<version>/` for what differs between versions, written
  from documented response shapes, not recordings.

## Tool definitions are a reviewed contract

Tools, their risk classes (`@ToolRisk`), resource references and policies reach the gateway through the manifest, and
the gateway administrator approves it. A changed name, title, description, input schema, risk or `@ResourceRef` changes
the tool's `definitionHash`; a changed policy file or `resource-types.json` changes `policiesHash`. Either one puts the
server into pending approval on every installation, and calls are refused until an administrator approves again.
So: do not rename tools or reword descriptions as a side effect of other work, keep each such change in its own PR,
and name it in the CHANGELOG entry. Update `ToolCatalog` (test), `GitLabPolicyDecisionsTest` and the tools table of the
README in the same change.

## Rules

- The server has no sign-in, does not decide who may call a tool and asks for no confirmation: the gateway does that.
  Do not add such checks. Resource-level decisions run in the starter's `ResourcePolicy` from the Cedar files; declare
  them with `@ResourceRef` instead of checking permissions in tool code.
- Contract first: a change that needs a different manifest field, resource type (a merge request, for example) or query
  field starts as a `proposed` entry in `CONTRACT_CHANGES.md` of `mcp-contracts`, and a person approves it first.
- A new tool needs `@ToolTitle`, `@ToolRisk`, `@ResourceRef` on the argument naming the project or group, a closed
  argument schema with bounded strings, a `ToolCatalog` entry, a test in the style of `RepositoryToolsTest` or
  `MergeRequestToolsTest`, and a README table row.
- No tool deletes anything, and there is deliberately no tool for an arbitrary API path or GraphQL. Keep it that way.
- An id below a project (issue, merge request, pipeline, job) is addressed under that project, and the answer must name
  the same project. Notes keep the quick action and `@all` checks of `GitLabArguments`.
- Job logs and artifact files pass through `JobLogText` redaction; a new secret pattern needs a test and a bounded regex.
- Text from GitLab goes to the model only through `UntrustedText`/`TextHygiene` from the starter.
- Map backend failures to the starter's `ToolErrorCode` in `GitLabToolErrors`. Never log or return the user's token or
  an `Authorization` header.
- Tests use `StubBackend` and dummy data only, never a real GitLab. Test methods are camelCase sentences
  (`theManifestPassesTheRulesOfTheGateway`).
- Add user-visible changes under `## Unreleased` at the top of `CHANGELOG.md`; the release commit renames it.
- The CI images are pinned by digest and actions by commit SHA; keep them pinned when you change them.

## Boundaries

Ask a person before you: tag, release, push to `main`, change the version in `pom.xml` or the starter version, publish an
image (images go to `ghcr.io` only, from `.github/workflows/release.yml` on a `v*` tag), or touch a real GitLab, gateway
or account. Never commit secrets, tokens, keys, certificates, filled `*.env` files (`deploy/mcp-gitlab.env` stays a
template), internal host names or IP addresses.

## Pull requests

One change per PR. Commit subject in English, imperative, up to 72 characters; the body says what changed and why, not
the process. Tests go in the same commit as the code. `./mvnw -B verify` must pass. Update README, `deploy/README.md` or
the CHANGELOG when behaviour visible to users or operators changes. See [CONTRIBUTING.md](CONTRIBUTING.md).
